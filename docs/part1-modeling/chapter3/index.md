# 第 3 章 显存占用估算：模型权重与 KV Cache

## 本章导读

> 第 1 章和第 2 章讨论的是推理速度：给定模型与硬件，生成每个 token 需要多少毫秒。把模型真正部署到服务器上之前，还要先回答另一个更基础的问题：这张显存有限的 GPU 能不能装下目标模型？装下权重之后，剩余显存又能同时服务多少条并发请求、支持多长的上下文？
>
> 3.1 把 GPU 显存拆成静态权重、每 token 键值缓存（KV Cache）和运行时开销三本账，并区分公式、框架分配器与设备驱动三种测量口径。3.2 将三本账合成为容量可行域，推导出最大并发数与最大上下文长度的兑换关系。3.3 在 RX 9070 XT 上依次验证权重、KV 缓存、激活峰值、碎片代理以及 vLLM 预分配池在饱和前后的运行表现。3.4 对所有实测残差做逐字节归因，并完成解析模拟器与 vLLM 实测 KV 池的闭合对账。章末实验与练习提供脚本命令与离线存档。

## 教学目标

- 能根据模型结构参数逐层计算静态权重参数量与显存占用，并说明权重共享（`tie_word_embeddings`）和数值精度对容量的影响。
- 能写出分组查询注意力（GQA）口径下每 token 的 KV 缓存字节数公式，并解释 GQA 相对多头注意力（MHA）的显存节省倍数。
- 能区分公式口径、PyTorch 分配器口径（`allocated` / `reserved`）与设备驱动口径（`rocm-smi`）的观测范围，说明激活工作区与分配器碎片的来源。
- 能根据显存预算手算最大上下文 $S_{\max}(B)$ 与最大并发 $B_{\max}(S)$，并解释 vLLM 预分配池满载时的排队与容量边界行为。
- 能将解析账本与真机实测逐项对账，把残差准确归因到运行时上下文、分配器块对齐取整或引擎预留开销。

## 3.1 显存的三本账

推理过程中的显存占用可以按生命周期分成三本账：模型加载后常驻不变的**静态权重**、随请求并发数与上下文长度动态增减的 **KV 缓存**，以及张量之外的**运行时开销**。用一套统一符号表示：

$$
\begin{aligned}
M_{\mathrm{weights}} &= N_{\mathrm{params}} \times b_{\mathrm{param}}, \\
m_{\mathrm{kv}} &= 2 \times L \times H_{\mathrm{kv}} \times D_{\mathrm{head}} \times b_{\mathrm{elem}}, \\
M_{\mathrm{avail}} &= M_{\mathrm{total}} \times u - M_{\mathrm{weights}} - M_{\mathrm{overhead}}.
\end{aligned}
$$

其中，$N_{\mathrm{params}}$ 为模型参数总数，$b_{\mathrm{param}}$ 和 $b_{\mathrm{elem}}$ 分别为权重与 KV 元素的每元素字节数（BF16 均为 2 字节），$M_{\mathrm{total}}$ 为显卡物理显存总量，$u \in (0, 1]$ 为允许推理引擎使用的显存比例。剩余可用显存 $M_{\mathrm{avail}}$ 决定了 KV 缓存池的容量上限。

### 3.1.1 静态权重

静态权重显存等于参数总数乘以单个参数的字节数。但模型名称中的“1.7B”“4B”只是近似量级，做容量规划时必须按层结构算出精确的 $N_{\mathrm{params}}$。以 **Qwen3-1.7B** 为例（$L = 28$ 层，隐藏维 $d = 2048$，查询头 $H_q = 16$，键值头 $H_{\mathrm{kv}} = 8$，单头维度 $D_{\mathrm{head}} = 128$，中间层维 $d_{\mathrm{inter}} = 6144$，词表大小 $V = 151{,}936$，无偏置项，启用输入输出权重共享 `tie_word_embeddings=true`），记 $d_q = H_q D_{\mathrm{head}} = 2048$、$d_{\mathrm{kv}} = H_{\mathrm{kv}} D_{\mathrm{head}} = 1024$，单层参数分解如下：

| 层内组件 | 参数量计算式 | 单层参数量 |
| --- | --- | ---: |
| `q_proj` | $d \times d_q = 2048 \times 2048$ | $4.194\;\text{M}$ |
| `k_proj` / `v_proj` | $2 \times (d \times d_{\mathrm{kv}}) = 2 \times 2048 \times 1024$ | $4.194\;\text{M}$ |
| `o_proj` | $d_q \times d = 2048 \times 2048$ | $4.194\;\text{M}$ |
| MLP（`gate` / `up` / `down`） | $3 \times d \times d_{\mathrm{inter}} = 3 \times 2048 \times 6144$ | $37.749\;\text{M}$ |
| `q_norm` / `k_norm` 与层归一化 | $d_q + d_{\mathrm{kv}} + 2d$ | $0.007\;\text{M}$ |
| **单层合计** | — | **$50.34\;\text{M}$** |

再加上全局词嵌入矩阵（$V \times d = 151{,}936 \times 2048 \approx 311.16\;\text{M}$）和末层归一化，由于输出头 `lm_head` 与词嵌入共享同一份存储（不重复计数），总参数量为：

$$
N_{\mathrm{params}} = 311.16\;\text{M} + 28 \times 50.34\;\text{M} = 1{,}720.7\;\text{M}.
$$

在 BF16（2 字节/参数）下，权重显存为 $1{,}720.7 \times 10^6 \times 2 / 2^{30} \approx 3.205\;\text{GiB}$。需要留意两个结构细节：第一，是否共享输入输出词表权重对中小模型影响显著——在 1.7B 上共享权重省去了约 311M 参数（0.577 GiB），Qwen3-0.6B、1.7B 和 4B 均启用了 `tie_word_embeddings=true`，而许多更大规模的模型不共享权重，计算时必须加回一份 $V \times d$。第二，不同数值精度直接缩放权重显存，决定了模型能否装进目标显卡：

| 权重精度 | 每参数字节数 | Qwen3-1.7B 权重 | Qwen3-4B 权重 |
| --- | ---: | ---: | ---: |
| FP32 | $4$ | $6.410\;\text{GiB}$ | $14.985\;\text{GiB}$ |
| **BF16（本章主线）** | **$2$** | **$3.205\;\text{GiB}$** | **$7.493\;\text{GiB}$** |
| FP8 / INT8 | $1$ | $1.603\;\text{GiB}$ | $3.746\;\text{GiB}$ |
| INT4 | $0.5$ | $0.801\;\text{GiB}$ | $1.873\;\text{GiB}$ |

FP32 下的 Qwen3-4B 仅权重就占 14.99 GiB，几乎占满 15.9 GiB 的 RX 9070 XT，根本没有空间留给上下文缓存。因此，数值精度首先是容量准入门槛，具体量化方法与精度权衡将在[第 4 章](/part1-modeling/chapter4/)展开。

### 3.1.2 每 token 的键值缓存（KV Cache）

自回归解码每生成一个新 token，都需要对之前所有历史 token 计算注意力。为了避免每一步重复投影历史 token 的键（Key）和值（Value），推理引擎把历史序列的 K、V 向量保存在显存中复用——本质上是用显存换算力的记忆化（memoization）。[Pope et al. (2022)](https://arxiv.org/abs/2211.05102)

每个 token 经过 $L$ 层 Transformer 时，需要在每一层写入 $H_{\mathrm{kv}}$ 个键向量和 $H_{\mathrm{kv}}$ 个值向量，每个向量维度为 $D_{\mathrm{head}}$。因此，每增加 1 个 token 所需的 KV 缓存字节数为：

$$
m_{\mathrm{kv}} = 2 \times L \times H_{\mathrm{kv}} \times D_{\mathrm{head}} \times b_{\mathrm{elem}}.
$$

代入 BF16（$b_{\mathrm{elem}} = 2$ 字节）与 Qwen3 结构参数，得到：

- **Qwen3-0.6B / Qwen3-1.7B**（$L = 28, H_{\mathrm{kv}} = 8, D_{\mathrm{head}} = 128$）：$2 \times 28 \times 8 \times 128 \times 2 = 114{,}688\;\text{B} = 112\;\text{KiB/token}$。
- **Qwen3-4B**（$L = 36, H_{\mathrm{kv}} = 8, D_{\mathrm{head}} = 128$）：$2 \times 36 \times 8 \times 128 \times 2 = 147{,}456\;\text{B} = 144\;\text{KiB/token}$。

公式中只出现键值头数 $H_{\mathrm{kv}}$，不出现查询头数 $H_q$。在标准多头注意力（MHA）下 $H_{\mathrm{kv}} = H_q$，1.7B 每 token 需要 224 KiB；分组查询注意力（GQA）将键值头减半至 8 个，使每 token KV 占用直接缩小为原来的 $H_{\mathrm{kv}} / H_q = 1/2$（在 4B 的 32q/8kv 结构上则缩小为 $1/4$）。

由公式可直接看出 KV 缓存的四个核心性质：其一，单条序列的 KV 显存 $m_{\mathrm{kv}} \cdot S$ 随序列长度 $S$ **严格线性增长**（注意力的 $O(S^2)$ 是计算量，不是持久化缓存显存）；其二，$m_{\mathrm{kv}}$ 与隐藏维 $d$、中间层维度及查询头数无关，因此参数量相差近三倍的 0.6B 与 1.7B 拥有完全相同的 112 KiB/token 缓存占用；其三，解码阶段每步追加 1 行且旧行在请求结束前不能释放，导致显存随生成长度单调上升；其四，预填充阶段一次性写入全部输入 token 的 KV 缓存，并叠加前向中间激活，常形成单次推理的瞬态显存峰值。

### 3.1.3 运行时开销与三个测量口径

静态权重与 KV 缓存之外，还有三类运行时开销会占据真实显存：

- **驱动与运行时上下文**：初始化 PyTorch 或推理引擎的 GPU 上下文后即常驻显存，与模型大小无关。
- **激活工作区（activation workspace）**：前向计算中存放注意力中间张量、矩阵乘临时输出的缓冲区，在预填充长序列时达到瞬态峰值，步末立即释放。
- **分配器碎片（fragmentation）**：框架显存池向设备申请大块显存后再按需切分给张量，反复申请和释放不同尺寸的张量后，未能合并归还设备的空闲块会形成显存空隙。

为了把理论账本与真机读数对齐，必须明确三个层次的测量口径：

| 测量口径 | 读取方式 | 观测对象与定位 |
| --- | --- | --- |
| 公式口径 | $N_{\mathrm{params}} b_{\mathrm{param}}$，$m_{\mathrm{kv}} S$ | 仅计张量净字节数，作为容量规划的理论下界 |
| 框架分配器口径 | `torch.cuda.memory_allocated()` / `memory_reserved()` | 分别反映存活张量总占用与分配器从设备保留的显存池总量（含空闲块） |
| 设备驱动口径 | `rocm-smi --showmeminfo vram`（或 `amdsmi`） | 驱动视角的总已用显存，等于运行时上下文、分配器保留池与非 PyTorch 占用之和 |

在解析估算阶段，通常用固定预留项 $M_{\mathrm{overhead}}$（例如 0.5 GiB）近似常驻运行时开销。3.3 与 3.4 节将用真机测量检验这一近似在裸 PyTorch 与 vLLM 预分配两种场景下的准确度。

## 3.2 容量可行域：并发与上下文的兑换

把三本账合在一起，剩余可用显存 $M_{\mathrm{avail}}$ 决定了显卡最多能容纳多少个 KV token，记为池总容量 $T_{\mathrm{pool}} = \lfloor M_{\mathrm{avail}} / m_{\mathrm{kv}} \rfloor$。在固定池容量下，给定并发请求数 $B$ 时的最大单请求上下文长度 $S_{\max}(B)$，以及给定每条请求上下文长度 $S$ 时的最大并发请求数 $B_{\max}(S)$ 互为反函数：

$$
S_{\max}(B) = \left\lfloor \frac{M_{\mathrm{avail}}}{B \cdot m_{\mathrm{kv}}} \right\rfloor,
\qquad
B_{\max}(S) = \left\lfloor \frac{M_{\mathrm{avail}}}{S \cdot m_{\mathrm{kv}}} \right\rfloor.
$$

以 **RX 9070 XT**（15.9 GiB 物理显存，取 $u = 0.9$ 即 14.31 GiB 预算，固定预留 $M_{\mathrm{overhead}} = 0.5\;\text{GiB}$，BF16 口径）为例，解析模块 `mem_ledger.py` 从模型配置文件直接读取结构参数，算出三款 Qwen3 模型的可行域：

| 模型 | 参数量 $N_{\mathrm{params}}$ | 权重 $M_{\mathrm{weights}}$ | $m_{\mathrm{kv}}$ | 可用 KV 池 $M_{\mathrm{avail}}$ | 池容量（token） | $B_{\max}$（$S=2048/4096/8192$） | $S_{\max}$（$B=1/4/16$） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Qwen3-0.6B | $596.1\;\text{M}$ | $1.110\;\text{GiB}$ | $112\;\text{KiB}$ | $12.700\;\text{GiB}$ | $118{,}897$ | $58\;/\;29\;/\;14$ | $118{,}897\;/\;29{,}724\;/\;7{,}431$ |
| Qwen3-1.7B | $1{,}720.7\;\text{M}$ | $3.205\;\text{GiB}$ | $112\;\text{KiB}$ | $10.605\;\text{GiB}$ | $99{,}287$ | $48\;/\;24\;/\;12$ | $99{,}287\;/\;24{,}821\;/\;6{,}205$ |
| Qwen3-4B | $4{,}022.6\;\text{M}$ | $7.493\;\text{GiB}$ | $144\;\text{KiB}$ | $6.317\;\text{GiB}$ | $46{,}000$ | $22\;/\;11\;/\;5$ | $46{,}000\;/\;11{,}500\;/\;2{,}875$ |

用 3.1 节的手算结果核对 Qwen3-1.7B 一行：$M_{\mathrm{avail}} = 15.9 \times 0.9 - 3.205 - 0.5 = 10.605\;\text{GiB}$；换算成 KiB 再除以 $112\;\text{KiB/token}$，得 $10.605 \times 1024^2 / 112 \approx 99{,}287\;\text{tokens}$；在 4096 上下文下最多同时容纳 $\lfloor 99{,}287 / 4096 \rfloor = 24$ 条请求，与程序输出逐位一致。

![RX 9070 XT 显存可行域堆叠图：对比 Qwen3-0.6B、1.7B 和 4B 的静态权重、固定预留与剩余 KV 池占比。模型越大，权重挤占越多，可供 KV 缓存使用的池子越小。](./images/fig1-ledger.png)

可行域表呈现出两条容量维度的核心规律：

1. **模型越大，可服务的上下文与并发反而越小**。在 14.31 GiB 预算下，0.6B 的权重仅占 7.8%，留出 12.70 GiB（11.9 万 token）给 KV 池；而 4B 的权重占去 52.4% 且每 token KV 增至 144 KiB，池容量缩水至 4.6 万 token，4096 上下文下的最大并发从 29 降到 11。
2. **上下文长度与并发数共享同一块固定池子**。$m_{\mathrm{kv}}$ 是两者的兑换率：1.7B 的 99,287 token 池既可以切成 24 条 4K 请求，也可以切成 3 条 32K 请求。这是[第 7 章](/part1-modeling/chapter7/)连续批处理受缓存块约束、以及[第 8 章](/part1-modeling/chapter8/) PagedAttention 消除块内浪费的物理前提。

若将显卡升级为 48 GB 显存档（以下按 48 GiB 标称容量与同样 $u = 0.9, M_{\mathrm{overhead}} = 0.5\;\text{GiB}$ 做解析估算，未上真机实测），权重占用保持不变，新增显存几乎全部进入可用 KV 池：

| 模型 | 权重 $M_{\mathrm{weights}}$ | 48 GB 档可用池 $M_{\mathrm{avail}}$ | 池容量（token） | $B_{\max}$（$S=4096 / 8192$） |
| --- | ---: | ---: | ---: | ---: |
| Qwen3-0.6B | $1.110\;\text{GiB}$ | $41.590\;\text{GiB}$ | $389{,}373$ | $95\;/\;47$ |
| Qwen3-1.7B | $3.205\;\text{GiB}$ | $39.495\;\text{GiB}$ | $369{,}763$ | $90\;/\;45$ |
| Qwen3-4B | $7.493\;\text{GiB}$ | $35.207\;\text{GiB}$ | $256{,}371$ | $62\;/\;31$ |

同样运行 Qwen3-4B，显存增大约 3 倍，可用 KV 池却从 46,000 token 跃升至 256,371 token（**5.6 倍**），$B_{\max}(4096)$ 从 11 增至 62。因为静态权重是固定门槛，超出权重之后的每一 GiB 显存都会直接转化为并发与上下文容量。

## 3.3 真机三口径对账与 vLLM 显存管理

下面在 **RX 9070 XT**（15.92 GiB，PyTorch + ROCm BF16 环境，以及 `vllm 0.29.0` 容器）上逐一验证三本账在真实硬件与推理引擎中的表现。

### 3.3.1 上下文底噪与静态权重对账

首先测量空卡和初始化 PyTorch 上下文后的设备级显存（数据见 `results/mem_real_9070xt.json`）：显卡无进程时的空闲读数为 **0.0559 GiB**；初始化 PyTorch GPU 上下文并创建一个极小张量后，`rocm-smi` 读数升至 **0.2519 GiB**（此时 `torch allocated = 0.0 GiB`，`reserved = 0.002 GiB`）。两者的差值 **+0.196 GiB** 是驱动与运行时上下文的固定底噪，与具体模型无关。因此，测量任何模型的净显存增量时，必须采用**差值法**，且基线取上下文初始化并释放旧模型后的读数，而不是完全空闲时的读数。

按此口径依次加载 Qwen3-0.6B、1.7B 和 4B（BF16），同时记录公式值、PyTorch 分配器读数与设备级差值：

| 模型 | 实测参数量 | 公式 $N \times 2\;\text{B}$ | `torch allocated` | `rocm-smi` $\Delta$ | $\Delta(\text{torch} - \text{公式})$ | $\Delta(\text{rocm-smi} - \text{公式})$ |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Qwen3-0.6B | $596.0\;\text{M}$ | $1.1102\;\text{GiB}$ | $1.1102\;\text{GiB}$ | $+1.1331\;\text{GiB}$ | $+0.0000\;\text{GiB}$ | $+0.0229\;\text{GiB}$ |
| Qwen3-1.7B | $1{,}720.6\;\text{M}$ | $3.2048\;\text{GiB}$ | $3.2053\;\text{GiB}$ | $+3.1981\;\text{GiB}$ | $+0.0005\;\text{GiB}$ | $-0.0067\;\text{GiB}$ |
| Qwen3-4B | $4{,}022.5\;\text{M}$ | $7.4924\;\text{GiB}$ | $7.5473\;\text{GiB}$ | $+7.5281\;\text{GiB}$ | $+0.0549\;\text{GiB}$ | $+0.0357\;\text{GiB}$ |

![权重显存三口径对账图：对比 Qwen3-0.6B、1.7B 和 4B 在公式口径、PyTorch allocated 口径与 rocm-smi 差值口径下的显存占用，三者高度重合。](./images/fig2-three-caliber.png)

三个模型的逐层手算参数量（596.1M / 1720.7M / 4022.6M）与实际 checkpoint 参数量偏差不到 0.01%。在 0.6B 和 1.7B 上，公式与 `torch allocated` 重合到 $\pm 0.001\;\text{GiB}$；在 4B 上，`torch allocated` 比公式高出 **+0.0549 GiB**（约占权重的 0.7%，3.4 节将逐字节归因到分配器块对齐）。设备级差值与公式偏差在 $\pm 0.04\;\text{GiB}$ 以内且正负不定，适合做量级核对，不宜作为精确账本。总体而言，静态权重公式 $N_{\mathrm{params}} \times b_{\mathrm{param}}$ 在真机规划中误差小于 1%。

### 3.3.2 键值缓存阶梯、激活峰值与碎片代理

接下来分别验证 KV 缓存线性增长、预填充瞬态激活峰值与分配器碎片代理（数据均来自 `results/mem_real_9070xt.json`）。

**纯张量 KV 阶梯**：依次持有 2048、4096 和 8192 长度的 KV 缓存张量且中途不释放，同时读取三个口径的累计增量：

| 模型（单 token KV） | 新增长度 $S$（累计持有） | 公式累计（GiB） | `torch` $\Delta$（GiB） | `rocm-smi` $\Delta$（GiB） |
| --- | ---: | ---: | ---: | ---: |
| Qwen3-1.7B（$112\;\text{KiB}$） | $2048$（$2048$） | $0.2188$ | $0.2188$ | $0.2188$ |
| Qwen3-1.7B（$112\;\text{KiB}$） | $4096$（$6144$） | $0.6562$ | $0.6562$ | $0.6562$ |
| Qwen3-1.7B（$112\;\text{KiB}$） | $8192$（$14336$） | $1.5312$ | $1.5312$ | $1.5311$ |
| Qwen3-4B（$144\;\text{KiB}$） | $4096$（$4096$） | $0.5625$ | $0.5625$ | $0.5625$ |
| Qwen3-4B（$144\;\text{KiB}$） | $8192$（$12288$） | $1.6875$ | $1.6875$ | $1.6874$ |

三口径在全部档位上偏差小于 $0.001\;\text{GiB}$，直接验证了 3.1.2 节的 GQA 字节公式。

**预填充瞬态激活峰值**：在 Qwen3-1.7B 上执行一次 $S = 4096$ 的真实预填充（`use_cache=True`），记录稳态占用与前向期间的 `max_memory_allocated`：前向结束后稳态显存为 **3.6428 GiB**（权重 3.2053 GiB + 4096 token KV 缓存 0.4375 GiB，与上表逐位吻合），而前向计算过程中的瞬态峰值达到 **4.8968 GiB**。两者的差值 **1.2539 GiB** 即为本次 4096-token 预填充的瞬态激活工作区；它在前向结束、临时输出释放后立即归零，不计入稳态账本，却决定了预填充瞬间是否会触发显存溢出。

**分配器碎片上界**：清空缓存后，连续执行 30 轮不同形状的显存申请与释放，最后释放全部存活张量。此时 `torch allocated = 0.0000 GiB`，但 `torch reserved = 0.1484 GiB`，设备级读数 `rocm-smi used = 0.2043 GiB`（恰好等于空闲底噪 0.0559 GiB 加上分配器保留的 0.1484 GiB）。这 0.1484 GiB 是框架分配器尚未归还设备的空闲块总量，构成外碎片的上界——它远小于模型权重和 KV 缓存的量级。

### 3.3.3 vLLM 启动预分配与 KV 池饱和行为

裸 PyTorch 在推理期间动态申请和释放张量；而生产级推理引擎 **vLLM** 采用**启动时预分配**策略：引擎启动时先加载权重，再用一次模拟前向测出给定批处理预算下的激活峰值，最后把剩余可用显存预算一次性全部划为 KV 缓存池。服务运行期间只在池内按块分配，不再向操作系统做大块设备显存申请。[Kwon et al. (2023)](https://arxiv.org/abs/2309.06180)

在 RX 9070 XT 上以 `enforce_eager=True`（关闭 CUDAGraph 缓存，使显存账本保持干净四项）串行启动 7 组不同 `(gpu_memory_utilization, max_model_len)` 配置，解析引擎启动日志中的显存分账（数据见 `results/vllm_probe_9070xt.json`）：

| 模型 | `util` | `max_model_len` | 权重（GiB） | 非权重常驻（GiB） | 激活峰值（GiB） | KV 池（GiB） | KV 池（token） | 名义并发上限 | 设备已用（GiB） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Qwen3-4B | $0.8$ | $4096$ | $7.56$ | $0.55$ | $0.60$ | $4.03$ | $29{,}344$ | $7.16\times$ | $12.7441$ |
| Qwen3-4B | $0.8$ | $8192$ | $7.56$ | $0.55$ | $0.60$ | $4.03$ | $29{,}344$ | $3.58\times$ | $12.7441$ |
| Qwen3-4B | $0.8$ | $16384$ | $7.56$ | $0.55$ | $0.60$ | $4.03$ | $29{,}344$ | $1.79\times$ | $12.7441$ |
| Qwen3-4B | $0.9$ | $4096$ | $7.56$ | $0.55$ | $0.60$ | $5.62$ | $40{,}928$ | $9.99\times$ | $14.3311$ |
| Qwen3-4B | $0.9$ | $8192$ | $7.56$ | $0.55$ | $0.60$ | $5.62$ | $40{,}928$ | $5.00\times$ | $14.3311$ |
| Qwen3-4B | $0.9$ | $16384$ | $7.56$ | $0.55$ | $0.60$ | $5.62$ | $40{,}928$ | $2.50\times$ | $14.3311$ |
| Qwen3-1.7B | $0.9$ | $8192$ | $3.22$ | $0.59$ | $0.41$ | $10.11$ | $94{,}640$ | $11.55\times$ | $14.4805$ |

![vLLM 启动显存四项分账图：展示权重、非权重常驻开销、激活峰值与预分配 KV 池之和严格贴合 gpu_memory_utilization 设定的显存预算。](./images/fig3-vllm-ledger.png)

每一行的账本恒等式都严格闭合：$\text{目标预算} = (\text{权重} + \text{非权重常驻}) + \text{激活峰值} + \text{KV 池}$。例如 4B 在 `util=0.9` 下，$14.33 = (7.56 + 0.55) + 0.60 + 5.62\;\text{GiB}$，且启动后设备级读数（14.3311 GiB）与预算几乎重合。对照表中的三组 `max_model_len` 可以得出两条关键结论：

1. **KV 池容量由物理显存和 `gpu_memory_utilization` 决定，不随 `max_model_len` 改变**。在同一模型与同一 `util` 下，无论 `max_model_len` 设为 4096、8192 还是 16384，KV 池容量都严格保持在 40,928 token。`max_model_len` 只决定单条请求的最大允许长度，因此日志报出的名义最大并发恰好等于 $\text{池容量} / \text{max\_model\_len}$（$9.99\times \to 5.00\times \to 2.50\times$）。
2. **激活预留由分块预填充的每步 token 预算决定**。vLLM 在 `max_num_batched_tokens=8192` 的默认分块预算下测出 4B 的激活峰值为 0.60 GiB（1.7B 为 0.41 GiB），这与 3.3.2 节裸 PyTorch 单发 4096-token 完整预填充测出的 1.2539 GiB 口径不同，两者不能直接相减。

::: details 工程备注：在 16 GiB 显卡上串行探测多个 vLLM 实例

| $2$ | $8{,}704$ | $21\%$ | $9.55$ | $0$ | $53.6$ |
| $4$ | $17{,}408$ | $42\%$ | $10.59$ | $0$ | $96.7$ |
| $8$ | $34{,}816$ | $85\%$ | $13.75$ | $0$ | $131.1$ |
| $16$ | $69{,}632$ | $170\%$ | $27.31$ | $0$ | $142.3$ |

![KV 缓存线性增长与 vLLM 并发压测图：左图展示三口径下纯 KV 显存随长度严格线性重合，右图展示并发超过 KV 池上限（170%）后总耗时翻倍、吞吐趋于平台。](./images/fig4-capacity.png)

当并发从 2 增至 8（占池 21%–85%）时，聚合吞吐从 53.6 tok/s 攀升至 131.1 tok/s，总耗时仅缓增至 13.75 s。当并发增至 16（总需求达池容量的 170%）时，总耗时几乎翻倍至 27.31 s，而聚合吞吐停在 142.3 tok/s 附近不再增长。整个过程抢占次数始终为 0：在启用分块预填充的调度器下，当 KV 池不足以接纳新请求时，引擎选择暂停接纳新预填充，把超出的请求留在等待队列中分两波完成，而不是报错拒绝或强行踢出正在生成的请求。这也再次说明，日志中的“名义并发 $5.00\times$”是按每条占满 8192 token 算出的最坏下界，实际可驻留并发取决于真实的请求长度（本例约 9.4 条）。

## 3.4 残差归因与模拟器对账

前面三节出现了四套口径（公式、PyTorch 分配器、设备驱动与 vLLM 内部账本）以及几处零点零几到零点几 GiB 的差值。本节把每一项残差归因到具体机制，使整本显存账完全闭合。

### 设备级读数与 `reserved` 池的对应关系

将 3.3.1 节顺序加载三个模型时的绝对显存读数摊开，并与“上下文基线 0.2519 GiB + `torch reserved`”逐行比对：

| 加载后时刻 | `torch allocated`（GiB） | `torch reserved`（GiB） | `reserved − allocated`（GiB） | `rocm-smi used`（GiB） | `0.2519 + reserved`（GiB） |
| --- | ---: | ---: | ---: | ---: | ---: |
| Qwen3-0.6B | $1.1102$ | $1.1328$ | $0.0226$ | $1.3850$ | $1.3847$（$\Delta +0.0003$） |
| Qwen3-1.7B | $3.2053$ | $4.3262$ | $1.1209$ | $4.5831$ | $4.5781$（$\Delta +0.0050$） |
| Qwen3-4B | $7.5473$ | $10.7598$ | $3.2125$ | $11.0194$ | $11.0117$（$\Delta +0.0077$） |

最右侧两列全部重合在 **$\pm 0.008\;\text{GiB}$** 以内，说明设备驱动口径观测到的就是“运行时上下文 + 分配器保留池”，与存活张量多少无直接关系。而中间一列 `reserved − allocated` 在加载 1.7B 时恰好约等于上一个模型 0.6B 的权重（1.1102 GiB + 0.0107 GiB 对齐余量），在加载 4B 时恰好约等于上一个模型 1.7B 的权重（3.2053 GiB + 0.0072 GiB 对齐余量）。这是因为模型对象存在 Python 引用环，`del model` 不会立即释放底层显存块，要等到垃圾回收触发后才归还分配器；在释放前，`empty_cache()` 也无法回收这些仍被标记为存活的块。由此也解释了为何 3.3.1 节采用“加载前后差值法”后设备级读数能与公式基本对齐，以及为何差值会带有 $\pm 0.04\;\text{GiB}$ 的小幅波动。

### 4B 权重 +0.055 GiB 残差的逐字节归因

在 3.3.1 节中，0.6B 与 1.7B 的 `torch allocated` 与理论公式误差均小于 0.001 GiB，唯独 Qwen3-4B 高出约 0.055 GiB。在干净上下文中单独加载 Qwen3-4B 并导出分配器内存快照（`results/residual_4b.json`），逐字节拆解结果如下：

| 拆解项 | 精确字节数 | 换算（GiB） |
| --- | ---: | ---: |
| `torch.cuda.memory_allocated()` | $8{,}101{,}709{,}824\;\text{B}$ | $7.5453\;\text{GiB}$ |
| 398 个模型参数存储净字节之和 | $8{,}044{,}936{,}192\;\text{B}$ | $7.4924\;\text{GiB}$ |
| `named_buffers`（2 个 FP32 RoPE 频率缓冲） | $512\;\text{B}$ | $\approx 0$ |
| 净残差（`allocated − params − buffers`） | **$56{,}773{,}120\;\text{B}$** | **$0.0529\;\text{GiB}$** |
| 内存快照 400 个活跃块的 $\sum(\text{块尺寸} - \text{请求尺寸})$ | **$56{,}773{,}120\;\text{B}$** | **$0.0529\;\text{GiB}$** |

最后两行**逐字节完全相等**。这证明全部残差既不是隐藏缓冲区，也不是驱动开销，而是 PyTorch 缓存分配器的 **size-class 块对齐取整**：Qwen3-4B 的 36 层 MLP 共有 108 个大权重矩阵（每个净大小 47.53 MiB），分配器将每个块向上取整到 48 MiB，单块产生 0.5 MiB 对齐余量，108 个大块累计就占去约 54 MiB。0.6B 和 1.7B 的单张量尺寸较小，对齐余量停留在 KiB 级，因此在 GiB 视角下几乎不可见。

### 解析模拟器与 vLLM 实测 KV 池的对账

最后核对 3.2 节的解析模拟器（假设 $M_{\mathrm{overhead}} = 0.5\;\text{GiB}$）与 3.3.3 节 vLLM 实测 KV 池的差异。在 Qwen3-4B（`util=0.9`）上，模拟器给出的 KV 池上界为 **6.317 GiB**（46,000 token），vLLM 实测 KV 池为 **5.62 GiB**（40,928 token），实测约为模拟上界的 **89%**。两者相差的 **0.697 GiB** 可以逐项完全闭合：

| 差额来源（模拟 − 实测） | 贡献（GiB） | 说明 |
| --- | ---: | --- |
| 总显存基准差 | $-0.020$ | 模拟取标称 $15.9 \times 0.9 = 14.31$，实卡为 $15.92 \times 0.9 = 14.33$ |
| 权重分配器取整差 | $+0.067$ | vLLM 实测权重 7.56 vs 公式 7.493 |
| vLLM 非权重常驻开销 | $+0.550$ | 进程运行时上下文与非 PyTorch 占用 |
| vLLM 激活峰值预留 | $+0.600$ | 启动 profiling 在分块预算下预留的激活空间 |
| 模拟器的固定预留项 | $-0.500$ | 3.2 节中已扣除的 $M_{\mathrm{overhead}}$ |
| **合计差额** | **$+0.697$** | 与 $6.317 - 5.620 = 0.697\;\text{GiB}$ 完全闭合 |

由此可见，vLLM 实际扣除的非权重非 KV 开销约为 $0.55 + 0.60 = 1.15\;\text{GiB}$。0.5 GiB 的固定预留对于裸 PyTorch 稳态估算偏保守，但对包含运行时上下文与激活预留的 vLLM 预分配池偏乐观。在 Qwen3-1.7B（`util=0.9`）上做交叉验证：模拟上界 99,287 token，vLLM 实测 94,640 token，对账率达到 **95%**（因为 1.7B 的权重取整与激活峰值都更小）。工程上做粗估时，将解析模拟器算出的 KV 池上界乘以 0.85–0.95 的经验折减，或直接把 $M_{\mathrm{overhead}}$ 设为 $1.0\text{–}1.2\;\text{GiB}$，即可逼近 vLLM 的真实池容量。

## 练习

1. 某模型共 $L = 32$ 层，隐藏维 $d = 4096$，采用 GQA（查询头 $H_q = 32$，键值头 $H_{\mathrm{kv}} = 8$，单头维度 $D_{\mathrm{head}} = 128$）。求 BF16 口径下每 token 的 KV 缓存字节数（单位 KiB）。如果改回 MHA（$H_{\mathrm{kv}} = 32$），每 token 占用会变为多少？
2. 一张 24 GiB 显存的 GPU 运行上述 BF16 模型（权重占 14.0 GiB），设定显存使用率上限 $u = 0.9$，预计非权重非 KV 运行时开销（含上下文与激活预留）为 1.2 GiB。计算可供 KV 缓存使用的显存 $M_{\mathrm{avail}}$、池容量（token 数），以及在单条请求平均长度 $S = 4096$ 时的最大并发数 $B_{\max}(4096)$。
3. 沿用第 2 题条件。如果将该模型权重从 BF16 量化到 INT4（权重降至约 3.8 GiB，KV 缓存仍保持 BF16 不变），可用 KV 池容量与 $B_{\max}(4096)$ 会分别变成多少？
4. 在 3.3.3 节的 vLLM 启动表中，Qwen3-4B 在 `util=0.9` 下无论 `max_model_len` 设为 4096 还是 16384，KV 池都固定为 40,928 token。某同学希望把 4B 在 8192 长度下的最大并发数提高一倍，于是将 `max_model_len` 从 16384 调小到 8192，期望以此腾出更多显存给 KV 池。这个操作能增大 KV 池吗？真正能增大 KV 池的手段有哪些？
5. 在裸 PyTorch 顺序加载两个模型后，设备驱动工具 `rocm-smi` 报告已用显存 8.50 GiB，而 `torch.cuda.memory_allocated()` 仅报告 5.20 GiB，同时 `torch.cuda.memory_reserved()` 报告 8.30 GiB，已知运行时上下文底噪为 0.20 GiB。说明这三个读数之间的关系，并解释为什么 `reserved` 会比 `allocated` 多出 3.10 GiB。
6. 3.3.2 节测得 Qwen3-1.7B 单发 4096-token 预填充的激活峰值为 1.2539 GiB，而 3.3.3 节 vLLM 对同一模型报告的激活峰值为 0.41 GiB。为什么同一模型的激活峰值读数相差超过三倍？能否用“1.2539 − 0.41”来计算 vLLM 省下了多少稳态显存？
7. 在 3.4 节的对账表中，为什么 0.5 GiB 的固定预留项在 Qwen3-4B（`util=0.9`）上高估了 vLLM 的 KV 池（模拟 46,000 token vs 实测 40,928 token）？如果要让解析模拟器在预测 vLLM 池容量时误差更小，应把 $M_{\mathrm{overhead}}$ 调整为包含哪两项开销？

::: details 参考答案

1. GQA 下 $m_{\mathrm{kv}} = 2 \times 32 \times 8 \times 128 \times 2 = 131{,}072\;\text{B} = 128\;\text{KiB/token}$。若改回 MHA（$H_{\mathrm{kv}} = 32$），键值头变为 4 倍，每 token 占用增至 $512\;\text{KiB/token}$。
2. 总预算 $24 \times 0.9 = 21.6\;\text{GiB}$；可用池 $M_{\mathrm{avail}} = 21.6 - 14.0 - 1.2 = 6.4\;\text{GiB}$。换算成 token 数：$6.4 \times 1024^2 / 128 = 52{,}428.8 \to 52{,}428\;\text{tokens}$。在 $S = 4096$ 下，最大并发 $B_{\max}(4096) = \lfloor 52{,}428 / 4096 \rfloor = 12$。
3. 权重降至 3.8 GiB 后，$M_{\mathrm{avail}} = 21.6 - 3.8 - 1.2 = 16.6\;\text{GiB}$；池容量增至 $\lfloor 16.6 \times 1024^2 / 128 \rfloor = 135{,}987\;\text{tokens}$；$B_{\max}(4096) = \lfloor 135{,}987 / 4096 \rfloor = 33$（并发上限提升近 2.75 倍）。
4. 不能增大 KV 池。vLLM 在启动时把预算内的剩余显存全部分配给 KV 池，`max_model_len` 只限制单条请求的最大允许长度，不改变池总容量。真正能增大 KV 池的方法包括：提高 `gpu_memory_utilization`、对权重或 KV 进行量化、减少 CUDAGraph/激活预留，或更换更大显存的显卡（以及多卡并行分摊权重）。
5. 设备级读数等于上下文底噪加上分配器保留池：$0.20 + 8.30 = 8.50\;\text{GiB}$。`reserved` 比 `allocated` 多出的 3.10 GiB 既包含分配器的块对齐与空闲缓存块，也常包含前一个已删除但尚未被 Python 垃圾回收彻底释放的模型张量块。
6. 两者测量的工作负载与执行机制不同：前者是裸 PyTorch 对单条 4096-token 序列一次性完成完整预填充时的瞬态峰值，后者是 vLLM 在分块预填充引擎与融合算子路径下按启动 profiling 预算测出的峰值。此外，激活工作区是瞬态峰值而非稳态常驻占用，因此不能直接相减并解释为“稳态节省”。
7. 因为 vLLM 预分配池时同时扣除了非权重常驻开销（0.55 GiB）和启动 profiling 测得的激活峰值预留（0.60 GiB），合计 1.15 GiB，加上 4B 权重块取整（0.067 GiB），远大于模拟器假设的 0.5 GiB。要提高对 vLLM 池容量的预测精度，应将 $M_{\mathrm{overhead}}$ 明确拆为“引擎运行时非权重常驻开销 + 激活峰值预留（若启用 CUDAGraph 还需加上图捕获预留）”。

:::
